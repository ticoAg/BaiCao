# 药典条目图谱化与证据节点处理设计

## 背景

当前仓库已经具备：

- `packages/knowledge_model/` 作为图模型共享真源的基础包
- `packages/data_ingestion/` 作为“图谱前”数据采集边界包
- `packages/api/app/pipeline/` 作为来源接入、预览、抽取与导出的主链路骨架

但面对 `ZJUFanLab/TCMChat-dataset-600k` 这类真实大文件来源时，现有能力还存在明显缺口：

- pipeline 的 `normalize / extract / map_to_knowledge_model` 仍偏 demo 逻辑，缺少按文件路由的专用处理器
- 共享图模型尚未完整覆盖“饮片”“证据”等本轮明确需要的业务对象
- 数据处理边界还没有形成“数据源路由 -> 文件处理器 -> 统一 bundle 输出”的稳定协议
- 对于药典这类长文本标准资料，系统还没有“规则切段 + LLM 结构化抽取 + Pydantic 边界校验”的正式设计

本轮用户已经明确希望：

- 以 `huggingface / pretrain/train/books/national_standard/2022年中药药典.txt` 为首个落地点
- 处理后进入图谱的数据必须带数据源信息
- 同一数据集下，不同文件可以走不同处理方法
- 每个文件拥有独立子目录定义模型与处理逻辑
- 公共数据模型、协议与路由能力上收共享模块
- 证据应作为图谱中的独立节点存在，且以“一个草药条目的完整原文块”为粒度
- 图谱中的内容型实体与关系优先使用中文表示，减少业务语义与技术标识之间的理解 gap

## 目标

### 主要目标

1. 为 `2022年中药药典.txt` 设计一条可扩展的图谱化处理链路
2. 采用 `protocol-first` 方式定义数据源路由、文件处理器、统一输出协议
3. 采用模块化设计，把文件专属逻辑隔离在独立处理器目录中
4. 采用“仅在边界处做一次数据校验”的策略，避免层层重复 parse / validate
5. 为每个草药条目产出：
   - 条目级 `证据` 节点
   - `药材` 节点
   - `饮片` 节点
   - `性味`、`归经`、`功效` 等首批高价值节点
6. 让所有结构化结果都带数据源与证据回链
7. 为后续同数据集其他文件、以及其他数据源文件处理器建立同一套扩展路径

### 非目标

- 首版不对整份药典全文一次性读取、一次性抽取
- 首版不把 `【性状】`、`【鉴别】`、`【检查】`、`【浸出物】`、`【含量测定】` 全量图谱化
- 首版不引入章节级证据节点或断言级证据节点
- 首版不对 `用于...` 中的全部病证短语做完整疾病节点归一化
- 首版不强制把每条 `炮制` 文本拆成独立 `工艺` 节点

## 用户确认后的边界

基于本轮沟通，已确认以下稳定约束：

- 证据节点的粒度是“一个草药条目的完整原文块”，不是章节级片段
- `饮片` 作为独立图谱节点存在，不是 `药材` 的附属字段
- `饮片` 与 `药材` 之间应保留专门关系，不仅仅复用 `工艺` 关系
- 图谱中的内容型节点与关系优先使用中文主称作为真源表达
- 文件处理器采用“规则切段 + LLM 结构化抽取 + Pydantic 边界校验”的平衡方案
- 模块化设计、`protocol-first`、边界单次校验是本轮实现的硬约束

## 方案对比

### 方案 1：规则切段 + 规则抽取少量字段

做法：

- 仅用规则完成条目切段、`性味与归经` / `功能与主治` 的简单抽取
- 不引入 LLM，尽量靠正则与字典匹配完成结构化

优点：

- 实现最快
- 调试路径短
- 对稳定格式字段可控性高

缺点：

- 对药典文本中的异常排版、缺失字段、炮制品命名、复杂措辞适应性较弱
- 后续扩展到不同文件体裁时很快碰到上限

### 方案 2：规则切段 + LLM 结构化抽取 + Pydantic 边界校验

做法：

- 先用规则把大文件切成“草药条目级证据块”
- 再对单个条目做规则章节拆分
- 最后把单条条目交给 LLM 生成文件专属结构化结果
- 文件专属结果经过 Pydantic 校验后，映射到共享图谱模型和统一导出 bundle

优点：

- 最符合当前文件结构与用户目标
- 兼顾可控性与抽取上限
- 最利于后续按文件扩展处理器

缺点：

- 需要同时建设路由协议、文件处理器、共享模型扩展与 LLM 抽取边界

### 方案 3：多阶段 LLM 断言系统

做法：

- 先做章节解析
- 再做断言级抽取
- 再做断言到图谱节点 / 边的组合与归并

优点：

- 长期表达能力最强
- 后续适合做细粒度证据追踪

缺点：

- 首版复杂度过高
- 与当前“条目级证据节点”目标相比范围明显偏大

## 推荐方案

推荐采用 **方案 2：规则切段 + LLM 结构化抽取 + Pydantic 边界校验**。

### 推荐原因

1. 这份药典文本具有稳定条目结构，适合先规则切块再逐块抽取
2. 文件很大，不适合整份读取；条目级处理可以天然支持增量、抽样和分批执行
3. 用户明确要求“统一处理后的数据 + 独立证据节点 + 数据源回链”，该方案最容易形成稳定闭环
4. 该方案最符合仓库当前的 `knowledge_model + data_ingestion + pipeline` 架构演进方向

## 设计决策

### 决策 1：采用四层模块边界

本轮设计按以下四层组织：

1. `packages/knowledge_model/`
   维护共享图谱真源，包括中文节点类型、中文关系类型、共享节点模型、共享边模型与导入记录

2. `packages/data_ingestion/`
   维护图谱前的共享协议，包括路由键、处理器协议、中间模型、统一 bundle 输出模型

3. 文件专属处理器目录
   例如：

   ```text
   packages/data_ingestion/data_ingestion/processors/huggingface/zjufanlab_tcmchat_dataset_600k/national_standard_2022_pharmacopoeia/
   ```

   用于承载 `2022年中药药典.txt` 的切段、章节解析、抽取模型、prompt、归一化与映射逻辑

4. 下游统一导出层
   统一消费 `UnifiedGraphBundle`，不关心来源文件内部细节

### 决策 2：采用三层路由键

文件处理器使用统一 `FileRouteKey` 路由：

- `provider`
- `dataset`
- `file_path`

本轮目标文件路由键为：

- `provider = huggingface`
- `dataset = ZJUFanLab/TCMChat-dataset-600k`
- `file_path = pretrain/train/books/national_standard/2022年中药药典.txt`

路由优先级采用：

1. 文件级精确匹配
2. 目录级匹配
3. 数据集级匹配
4. provider 级 fallback

### 决策 3：证据节点以条目完整原文块为粒度

每个草药条目产出一个独立 `证据` 节点，至少包含：

- `raw_text`
- `source`
- `source_provider`
- `dataset_name`
- `file_path`
- `entry_title`
- `line_start`
- `line_end`
- `chunk_hash`

证据节点不拆成章节级节点。章节信息只作为条目内部可解析结构存在，供结构化抽取与映射使用。

### 决策 4：`饮片` 为独立节点

药典条目中的 `饮片` 段落不作为 `药材` 的附属字段存在，而是映射成独立 `饮片` 节点。

主药材与饮片之间使用中文关系表示，例如：

- `药材 -> 具有饮片 -> 饮片`

若后续需要再表达 `炮制` 过程，可在不破坏首版模型的前提下，再补 `工艺` 节点及其关系。

### 决策 5：内容型节点与关系以中文为真源

本轮新增与补齐的内容型图谱对象优先使用中文主称：

- 节点：
  - `药材`
  - `饮片`
  - `证据`
  - `性味`
  - `归经`
  - `功效`
  - `来源`

- 关系：
  - `具有饮片`
  - `具有性味`
  - `归于经脉`
  - `具有功效`
  - `由证据支持`

如系统内部确需兼容英文技术值，可维护一层内部映射，但中文表达是共享模型的业务真源。

### 决策 6：LLM 只承担条目级结构化抽取职责

LLM 仅处理单个条目的已切段、已拆 section 输入，不负责：

- 整文件切段
- 文件路由
- 新 schema 发明
- 共享图谱模型直出
- 跨条目推理

LLM 输出的是文件专属抽取模型，不是共享图谱模型。

### 决策 7：边界单次校验

采用“只在边界处校验一次”的约束：

1. 原文进入条目块边界时校验一次
2. 条目块进入文件专属抽取结果边界时校验一次
3. 文件专属抽取结果进入共享图谱模型边界时校验一次

边界内部优先传递 typed object，不对同一对象重复执行多轮 `model_validate`。

## 文件级处理流水线

### 1. `source_context`

读取最小必要上下文：

- `provider`
- `dataset`
- `file_path`
- 本地绝对路径
- 文件大小
- 行数

### 2. `entry_segmentation`

采用规则切段，把大文件切成 `RawEntryBlock`。

切段规则以稳定结构锚点为基础：

- 中文药名标题行为条目起点
- 后续可跟拼音 / 拉丁 / 英文规范名
- 直到下一个条目起点前，全部内容都属于当前条目

### 3. `entry_parsing`

对单条条目做规则级章节拆分，提取：

- 标题区
- 基础描述
- 常规 section
- `饮片` section 及其子段落

### 4. `evidence_building`

不依赖 LLM，先稳定构造 `证据` 节点。

### 5. `llm_extraction`

基于单条条目的章节化输入抽取：

- `药材`
- `饮片`
- `性味`
- `药性`
- `归经`
- `功效`
- `用法与用量`
- `注意`
- `贮藏`
- `炮制文本`

无法确认的字段显式留空，不允许补充常识。

### 6. `pydantic_validation_and_normalization`

分两层处理：

1. 文件专属抽取模型校验  
   确保 LLM 输出符合本文件允许的结构

2. 共享图谱模型映射校验  
   确保节点类型、关系类型、数据源字段、证据回链等满足共享真源要求

### 7. `graph_export_bundle`

统一输出 `UnifiedGraphBundle`：

- `nodes`
- `edges`
- `records`
- `warnings`
- `errors`
- `stats`

## 图谱映射规则

### 首版稳定产出的节点

对于单个条目，首版稳定产出：

- `药材`
- `饮片`
- `证据`
- `性味`
- `归经`
- `功效`

### 首版稳定产出的关系

- `药材 -> 具有饮片 -> 饮片`
- `药材 -> 具有性味 -> 性味`
- `药材 -> 归于经脉 -> 归经`
- `药材 -> 具有功效 -> 功效`
- `饮片 -> 具有性味 -> 性味`
- `饮片 -> 归于经脉 -> 归经`
- `饮片 -> 具有功效 -> 功效`
- `药材 -> 由证据支持 -> 证据`
- `饮片 -> 由证据支持 -> 证据`

若条目中对应字段仅出现在 `饮片` 段落，则首版优先将其挂到 `饮片`，不强行复制到 `药材`。

### ID 与去重规则

建议采用可重复生成、可 merge 的 ID：

- `证据:{provider}:{dataset}:{file_path}:{entry_title}:{hash}`
- `药材:{name}`
- `饮片:{name}`
- `性味:{name}`
- `归经:{name}`
- `功效:{name}`

首版去重采用轻量规范化，不做激进语义归并。

## 首版最小落地范围

### 首版必须完成

1. 文件级路由闭环
2. 条目级切段
3. 条目级证据节点产出
4. `药材 / 饮片 / 性味 / 归经 / 功效` 节点产出
5. 中文关系产出
6. 统一 bundle 输出

### 首版暂不处理

- `【性状】`
- `【鉴别】`
- `【检查】`
- `【浸出物】`
- `【含量测定】`
- 章节级证据节点
- 断言级证据节点
- 全量病证节点归一化
- 全量工艺节点抽取

## 实施顺序建议

1. 扩展 `packages/knowledge_model/` 的中文节点与关系真源
2. 扩展 `packages/data_ingestion/` 的共享协议与路由注册表
3. 为 `2022年中药药典.txt` 新增文件专属处理器目录
4. 实现条目切段与章节解析
5. 实现文件专属 LLM 抽取模型与 prompt
6. 实现共享图谱映射与统一 bundle 输出
7. 最后接入 API pipeline 或 CLI 入口

## 首版成功标准

1. 处理器能命中本地缓存文件：

   ```text
   .cache/huggingface/ZJUFanLab/TCMChat-dataset-600k/pretrain/train/books/national_standard/2022年中药药典.txt
   ```

2. 能把文件切成稳定的草药条目级证据块

3. 对样例 `一枝黄花`，能稳定产出：

- 1 个 `药材`
- 1 个 `饮片`
- 1 个 `证据`
- 若干 `性味`
- 若干 `归经`
- 若干 `功效`
- 对应中文关系

4. 所有结构化结果都带数据源信息与证据回链

5. 所有生成结果都经过边界 Pydantic 校验

## 风险与后续扩展

### 风险

- 中文药名条目起点规则可能被 OCR 噪声或排版异常打断
- `饮片` 段落中的个别条目可能缺字段或混入异常标题
- 同一功效短语在不同条目中存在轻微变体，首版只做轻量规范化

### 后续扩展方向

- 同目录其他国家标准文件处理器
- `病证` 节点与关系抽取
- `工艺` 节点映射
- 章节级或断言级证据体系
- 批量离线处理与回放导入
