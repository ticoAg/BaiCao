# 数据处理工作台设计

## 背景

当前仓库已经具备导入器和图谱工作台雏形：

- 后端已有 CSV / JSONL 导入器与 dry-run 预览能力
- 前端已有 `/graph/workbench` 工作台页和结果帧交互模式

但面对接下来要处理的多种数据来源，现有能力还不够：

- 只能做一次性导入，不支持持久化处理任务
- 没有固定步骤模板，不利于多来源共用
- 没有“每一步可预览、人工确认后进入下一步”的交互
- 没有把非结构化数据处理正式纳入项目主路径

与此同时，项目已经确认：

- 图模型必须有仓库级唯一真源
- 数据采集是二级子项目
- 非结构化数据要支持“规则 + agent”的混合处理

这意味着需要一个新的工作台来承接“多来源 -> 规范化 -> 抽取 -> 映射 -> 人工确认 -> 导出 / 入库”的完整流程。

## 目标

### 主要目标

1. 提供一个独立的数据处理工作台页面
2. 使用固定通用步骤模板处理各种来源数据
3. 每一步支持预览、重跑、人工确认、回退
4. 把整个流程持久化为可恢复的处理任务
5. 在第 5 步与共享图模型唯一真源正式对接

### 非目标

- 不在本轮实现批量自动化编排平台
- 不在本轮支持任意用户自定义步骤模板
- 不在本轮直接接入所有外部来源
- 不在本轮把前端做成可视化 DAG 编辑器

## 用户确认后的边界

本轮已经确认：

- 操作面以 **Web 页面** 为主
- 可以单独有一个页面处理数据管道
- 处理任务需要可保存、可恢复
- 所有来源走**固定的通用步骤模板**
- 来源适配可以不同，但整体步骤不分叉

## 方案对比

### 方案 1：线性向导

优点：

- 简单
- 实现快

缺点：

- 回看历史困难
- 人工修订与差异对比体验差
- 不适合长期处理任务

### 方案 2：步骤工作台

优点：

- 适合固定模板
- 很自然支持预览、确认、重跑、回退
- 与现有 `/graph/workbench` 的工作台组织方式相容

缺点：

- 比一次性向导略重

### 方案 3：看板流

优点：

- 适合大量任务并行管理

缺点：

- 第一版过重
- 单任务细粒度预览不如工作台直观

## 推荐方案

推荐采用 **步骤工作台**。

原因：

1. 它最贴合“固定步骤模板 + 每一步可预览 + 人工放行”的需求
2. 它能复用现有 `workbench` 的交互语言
3. 它天然适合“可保存、可恢复”的处理任务模型

## 设计决策

### 决策 1：页面采用三栏工作台

推荐结构：

- 左侧：步骤轨
- 中部：操作面板
- 右侧：预览区

### 决策 2：任务对象作为主驱动

工作台不是临时导入向导，而是围绕一个持久化任务运转。

主对象：

- 中文：处理任务
- 英文技术名：`PipelineRun`

### 决策 3：步骤之间默认人工放行

步骤内可以自动运行，但关键步骤之间不自动推进。

用户必须：

- 先运行预览
- 再确认进入下一步

### 决策 4：固定 7 步模板

固定步骤如下：

1. 接入来源
2. 原始内容预览
3. 规范化清洗
4. 结构抽取
5. 映射到共享图模型
6. 人工确认与修订
7. 导出 / 入库

### 决策 5：第 5 步成为图模型真源边界

工作台直到第 5 步才进入统一图模型映射。  
这使得前面步骤可以处理各种来源与中间结构，但不会污染正式图谱定义。

## 交互设计

### 左侧步骤轨

每一步展示：

- 步骤名称
- 当前状态
- 最近更新时间
- 是否可进入

### 中部操作区

当前步骤展示：

- 目标说明
- 参数配置
- 主操作按钮

主操作按钮：

- `运行预览`
- `确认进入下一步`

辅助操作：

- `重新运行`
- `退回上一步`
- `保存草稿`
- `暂停任务`

### 右侧预览区

根据 `preview_kind` 渲染不同组件：

- `text`
- `table`
- `candidate_entities`
- `candidate_relations`
- `graph_mapping`
- `diff`
- `error_list`
- `summary`

## 数据模型

推荐至少包含：

- `PipelineRun`
- `PipelineStepRun`
- `PipelineArtifact`
- `PipelineReviewAction`

## 后端设计

推荐后端结构：

```text
packages/api/app/pipeline/
├── service.py
├── storage.py
├── models.py
├── schemas.py
├── steps/
└── adapters/
```

职责：

- `service.py`：管理任务流转
- `storage.py`：管理产物与预览
- `models.py`：任务与步骤状态模型
- `schemas.py`：API schema
- `steps/`：固定步骤处理器
- `adapters/`：来源适配器

## 前端设计

推荐前端结构：

```text
packages/web/src/
├── pages/DataPipelinePage.tsx
├── components/pipeline/
├── hooks/usePipelineRun.ts
├── services/pipelineApi.ts
├── stores/pipelineStore.ts
└── types/pipeline.ts
```

## 与共享图模型的关系

该工作台不是图模型真源，只是消费者。

关系如下：

- 第 1 到第 4 步：处理来源与候选结果
- 第 5 步：映射到共享图模型真源
- 第 6 步：人工修订共享模型实例
- 第 7 步：把确认后的共享模型实例交给导入器或正式入库

## 风险与控制

### 风险 1：页面过重

控制方式：

- 第一版只实现单任务视图
- 任务列表和批量操作放到后续版本

### 风险 2：预览协议碎片化

控制方式：

- 所有步骤统一返回 `preview_kind + preview_payload`
- 前端按类型渲染，不为每一步单独造协议

### 风险 3：中间结果污染正式图谱

控制方式：

- 只有第 7 步允许正式入库
- 第 1 到第 6 步只保存处理中产物

## 结果

本轮设计确认：

- 数据处理工作台采用独立页面
- 处理主线使用固定步骤模板
- 每一步可预览、可重跑、可确认、可回退
- 整体处理过程持久化为可恢复任务
- 第 5 步与共享图模型唯一真源对接
